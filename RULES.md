# Repository rules

Apply the rules relevant to your change. [CONTRIBUTING.md](CONTRIBUTING.md) owns the project
layout, commands, and test selection; the rows below link to it rather than repeat it.

## Code conventions and structure

| Rule | How to apply |
| --- | --- |
| Treat the code as the authority for the domain model and its capabilities. | Read the minimum code and docs needed to avoid guessing. Narrative pages under `docs/` may lag the code and do not substitute for reading it. When docs and code disagree, report it plainly instead of guessing. Do not restate the domain model, its vocabulary, or the current Source and Destination capabilities in agent guidance, where a copy drifts silently and is then read as instruction. |
| Follow established formatting, naming, and language conventions. | Follow [.editorconfig](.editorconfig); use nearby code where it leaves a choice open. C# runs with nullable reference types and implicit usings enabled; types, methods, and properties are PascalCase, locals and parameters camelCase, database columns and `Connector.key` values `snake_case`. Prefer early returns over deep nesting. Do not mistake scaffold or template code for intended final architecture. Run `dotnet format Integrios.slnx` on touched C#, which CI does not check. The dashboard's Biome configuration is checked by `biome ci` inside `npm --prefix src/Integrios.Admin/frontend run check` and the CI dashboard build. Correct demonstrated defects within scope rather than copying them for consistency. |
| Respect established boundaries between components. | Review affected responsibilities and dependencies against the [control plane and data plane split](docs/architecture.md#control-plane-and-data-plane). Ingestion owns intake, Tenant resolution, and acceptance-boundary writes, not fanout, delivery, or retry. Admin owns control-plane configuration and its write path, not Event processing, and its authority never becomes Tenant-scoped. Worker owns outbox polling, fanout, delivery, and retry, dead-letter, and replay, not HTTP intake or configuration writes; it reads configuration straight from the database, and no service calls another for configuration. Domain owns entities, enums, and value objects, not ports, handlers, persistence, or API contracts. `tests/Integrios.ArchitectureTests` enforces dependency direction, the ports each host may resolve, exactly-one-host handler registration, and banned names and folders; run it for any backend change. Correct boundary defects within scope without introducing unnecessary layers or an unrelated redesign. |
| Keep the core provider-neutral. | No Domain type, routing rule, or delivery behavior names a provider or makes a business decision. Provider-specific transport and parsing stay at the Source boundary, in Ingestion's adapters and Operator-authored Connector manifests. Source and Subscription mappings stay stateless; logic that needs another system's current state belongs in the downstream system, not in a richer mapping. Review only. |
| Stay within the current scope boundaries unless the change is meant to move them. | OperatorUsers sign in through OpenID Connect or an optional Integrios-managed password credential, with no public signup or email recovery. There is no role or permission model yet: every signed-in OperatorUser holds the same authority. Every feature is Tenant-aware from the start, and idempotency, replay, retries, and dead-lettering are platform concerns, not left to each integration. A change that moves one of these boundaries says so and updates this row. |
| Keep Operator-facing configuration typed and documented. | Put new Operator-facing non-secret defaults in the role's `appsettings.<role>.json` with environment-variable overrides, and update [the settings reference](docs/configuration.md) when a key or default changes. Read and validate related fixed settings during host composition, then inject an immutable typed value; use `IOptions<T>` where it simplifies a touched section, and keep CLI validation paths working. Simple host settings may be read directly during composition. Tenant secret references are open-ended keys resolved per Tenant from `IConfiguration`. |
| Reuse established patterns and add complexity only for a concrete benefit in the current change. | Look for an existing port in `src/Integrios.Application` or adapter in `src/Integrios.Infrastructure` before adding one. Extract helpers for reuse, complex boundaries, or clearer callers; keep simple single-use expressions inline. Correct defective patterns within scope. Avoid speculative hardening while retaining required security, failure handling, and data protections. |
| Make code express its intent; reserve comments for information the code cannot convey. | Prefer clear names and structure over comments that narrate behavior or explain confusing code. Remove redundant and stale comments and commented-out code. Preserve required legal notices, public API contracts, and verified external constraints or rationale. Keep refactoring within scope. |
| Fix the underlying cause and remove recurring failure paths where practical. | Trace the failure before changing code. Prefer correcting the owning logic, simplifying the design, or making invalid states impossible over adding workarounds. Keep changes within scope; explain necessary workarounds and their limits. |
| Complete the requested change and preserve unrelated work. | Review affected callers, configuration, tests, migrations for both providers, and the full diff for missing updates. Update [the settings reference](docs/configuration.md) when a key or default changes, and the public pages under `docs/` when behavior they describe changes; never leave an architectural decision recorded only in code. Update or remove affected examples, comments, and agent guidance so they describe the resulting behavior and no longer prescribe obsolete workarounds. Preserve unrelated edits and avoid unrelated cleanup. |

## Domain and Application structure

| Rule | How to apply |
| --- | --- |
| Organize Domain by type kind, one type per file. | `src/Integrios.Domain` holds `Entities/`, `Enums/`, and `ValueObjects/`, each its own namespace, and no ports, handlers, or persistence concerns. An entity has its own identity and lifecycle; anything without an Id is a value object, however large. Moving or renaming a Domain type changes the CLR type names recorded in both providers' EF Core model snapshots; update those literals in the same change. Folder layout and snapshot updates rely on review. |
| Organize Application by responsibility group, then capability. | One folder per capability, never layered buckets. `Commands/` and `Queries/` hold the operations, their handlers, and support used only by that kind; `Models/` holds only `*Dto` types shared by more than one operation; the capability root holds ports and rules shared across kinds or with Infrastructure and hosts. `Common/` holds only cross-capability primitives. Namespaces are `Integrios.Application.<Group>.<Capability>`, collapsing to `<Group>` when a group holds one capability, and never name the operation folder. Each host registers handlers by group namespace; name a handler owned by another host explicitly at its composition root. Name folders for the responsibility they own, never for a host, deployment tier, or actor role. `SourceTree_HasNoGenericContractBuckets` bans `Contracts/`, `Interfaces/`, and `Abstractions/` in `src/`; the approved group list in `ApplicationArchitectureTests.cs` and the handler-ownership tests in `HostCompositionArchitectureTests.cs` tie groups to hosts. A `Services/` folder is banned by review only. |
| Name each Application output for what it is. | A `*Dto` projects persisted state plus projection metadata such as a pagination cursor, never deployment configuration, request context, or facts about one execution. A `*Result` describes an execution or computation outcome, and a `*Report` a diagnostic collection. Name by the output, never by command versus query or by host. Keep paged lists per capability. `Application_NeverDeclaresGenericResultWrapper` and `ApplicationTypes_AreNeverNamedResponse` enforce the bans on a generic `Result<T>` and on Application `*Response` types. |
| Give every host endpoint its own wire types. | Bind each endpoint to a host-owned `*Request`; route values are authoritative and no body restates them. Never bind a `*Command` or `*Query` straight off the wire: deserialization ignores nullability, so untrusted input must become trusted in exactly one place. Define a `*Response` only where the host contributes something the use case cannot know; otherwise serialize the Application output directly. `ApplicationTypes_CarryNoRequestVocabulary` keeps request types out of Application; binding relies on review. |
| Design ports around the capability, never the vendor. | Name the port for its capability and the implementation for its vendor; `*Service` is banned as a suffix. No vendor or package type crosses a port signature, so a fake compiles with no packages; a platform type that is itself domain vocabulary is allowed. Declare no default parameter values, put `CancellationToken` last, and pass it at every call site. Write-side repositories take and return domain entities or capability values, never Dtos; read-side `*Lookup` or `*Queries` types, never `*Repository`, project persisted state straight to a Dto. Adapters return an expected "no" semantically, as `T?` for not-found, a flag for an idempotent replay, or `bool` for did-it-happen, and throw on timeouts, connection failures, and auth errors. Add a seam only when a concrete caller needs less authority or a fake is forced to throw on members it never uses. `ApplicationPortSignatures_ReferenceOnlyDomainApplicationOrBcl`, `PortInterfaces_DeclareNoDefaultParameterValues`, and `ProductionTypes_NeverUseServiceSuffix` enforce the signature, default, and suffix rules. |
| Place each type beside its only reason to exist. | A single-owner Dto sits next to its operation, a shared Dto in the capability's `Models/`, a result with its command or query, and a port's input and output records inside the interface file so the seam reads as one contract. A type shared across operations or carrying independent meaning gets its own file. Capability values carry ubiquitous-language names, never `*Details`, `*Info`, or `*Data`; `DomainTypes_NeverUseReservedCapabilitySuffixes` enforces this for Domain types, and Application relies on review. |
| Map by hand and set JSON casing once per host. | Map with a static `From(...)` on the type that owns the mapping, and compose capability results inline in handlers; use no mapping libraries or profiles. JSON is snake_case by a policy set once per host; enum representations and passthrough JSON payloads round-trip with their original keys. `SourceTree_DeclaresNoJsonPropertyNameAttributes` bans per-property casing attributes; mapping relies on review. |

## Input, security, and failure handling

| Rule | How to apply |
| --- | --- |
| Validate untrusted input at its owning boundary and rely on those guarantees internally. | Untrusted input enters through Ingestion's intake (webhooks, the Event API, broker Sources) and the Admin API. Validate it there, and verify the invalid-input cases before relying on its guarantees downstream. Avoid repeating checks for guarantees the boundary actually establishes. |
| Preserve required security checks and protections against data loss. | Review Source verification, TenantApiKey and Operator authentication, Tenant isolation, the durable acceptance boundary, and destructive actions. Source secrets resolve only in Ingestion and destination secrets only in the Worker; the per-host checks in `tests/Integrios.ArchitectureTests` enforce this. Exercise relevant negative cases in `tests/Integrios.FunctionalTests` to confirm protections still work after the change. |
| Preserve useful failure information and handle errors at the responsible layer. | Propagate errors with useful context; recover or report at the layer that owns that responsibility. Avoid catches that obscure the cause. Exercise failure paths to confirm that a rejected intake or a failed delivery can never be recorded as accepted or delivered. |

## Platform support

| Rule | How to apply |
| --- | --- |
| Support native Windows and Linux equally. | Never fix a Windows failure by requiring WSL, and never weaken Linux or POSIX behavior to make Windows tests pass. Use platform-native paths and APIs where hosts differ, keep container paths Linux-native, and never force one textual path layout everywhere. Contributor commands assume no Linux-only host features: no host networking, host `/run` paths, POSIX FIFOs, shell-only syntax, or `/`-only path parsing; prefer pinned Compose services and Compose service DNS, and use a Linux helper container when a test needs POSIX filesystem semantics. Keep per-OS build output separate, so a WSL run against a Windows checkout never reuses its `bin` and `obj`. Verify on both platforms with the narrowest relevant test project, and separate product failures from environment failures such as unavailable Docker, missing mounts, or mixed build output. CI runs only on Linux, so Windows behavior relies on local verification. |

## Verification

| Rule | How to apply |
| --- | --- |
| Encode requirements in automated checks when violations can be detected reliably. | Prefer existing types and API boundaries, then `tests/Integrios.ArchitectureTests` for structural requirements, then a targeted behavioral test. Land a new rule's check in the same change as the rule. Verify that the check rejects a representative violation and accepts valid cases. Make failures explain the violated requirement and expected correction. Keep judgment-based decisions in written guidance. |
| Verify the change with evidence appropriate to its behavior. | Choose tests with [Choosing tests](CONTRIBUTING.md#choosing-tests); a docs change runs `npm run docs:build`, which fails on broken internal links. Write tests with xUnit, and add or update tests when behavior changes. Exercise integrations, runtime behavior, or the dashboard when the claim depends on them, including browser checks when layout or focus matters. Distinguish pre-existing failures and state what remains unverified. |
| Prevent demonstrated regressions with targeted checks where practical. | Reproduce the failure; show the check rejects it and accepts valid behavior, or explain the limitation. Prefer extending existing tests or checks over introducing a framework or brittle wording assertions. |
| Test the dashboard's own contract, and prove browser flake fixes under the conditions that failed. | A real anchor with the correct `href` already owns open-in-new-tab and middle-click; prove the URL and the dashboard's normal navigation instead of asking headless Chromium to open a second tab. Keep real-browser coverage for what jsdom cannot decide: layout, focus order, visible focus, custom listboxes, pointer gestures, and responsive interaction. A Windows or single-file pass does not clear a Linux full-suite failure, because parallel Vite servers and browser workers create the load that exposes timing-sensitive tests; start with the failing file, then repeat the full frontend suite on Linux. A `-t` filter may skip earlier tests that warm a cold Vite server, so keep file order or warm the server explicitly. Prove a fix with the same stress loop that reproduced it, without retries and stopping on the first failure, and record pre-fix reproduction and post-fix pass counts. More retries or a longer timeout are not a fix unless measurement shows the operation legitimately needs that time. |
| Preserve meaningful validation instead of weakening checks merely to pass. | Review tests, suppressions, exclusions, and CI changes. Keep restores in `--locked-mode`, the dependency audits, and every test project in CI; do not partition a test project with traits or category filters. Investigate suppressions before adding or retaining them; fix the underlying issue when the check identifies a real defect. Update expectations when intended behavior changes; justify exceptions narrowly and preserve checks that detect incorrect behavior. |

## Source hygiene

| Rule | How to apply |
| --- | --- |
| Write commit messages as Conventional Commits. | Use `<type>(<scope>): <description>` with the types and scopes in [Commit messages](CONTRIBUTING.md#commit-messages). Release versions are derived from these messages, so a `feat` makes a minor and a `fix` a patch; see [Cutting a release](docs/ci-cd.md#cutting-a-release). |
| Keep secrets and unintended local state out of tracked source. | Supply Tenant secret values through the files described in [secrets/README.md](secrets/README.md) and deployment credentials through environment variables. `.gitignore` excludes those files except the sanitized examples, along with `.env`, `*.local.md`, and the local Azure deployment files under `deploy/azure/`; no CI step scans for secrets, so inspect tracked changes before committing. |
| Keep private planning out of the public repository. | The repository is public. Do not name private decision records, roadmap items, or paths inside the private context directory in code, tests, docs, commit messages, or pull request text; state the reason in plain terms. `tests/Integrios.ArchitectureTests` enforces this for C# under `src/` and `tests/`, and the docs workflow checks that `*.local.md` content stays out of the published site. Everything else relies on review. |
